Retry is the cheapest way to turn a random failure into a success: run the same request again. It is also the easiest way to turn a small outage into a large one, because retries add load to a dependency at the moment it can least afford it.

## Also known as

- **Retry** — the pattern, and the name this page uses.
- **Backoff** — the wait between attempts. Capped exponential backoff is the common form. It is the policy inside a retry, not the whole of it.
- **Jitter** — randomness added to the backoff, so clients do not wait the same amount. A part of the retry, and the part most often left out.
- **Retry budget** — a cap on retry traffic across a fleet. Google's SRE book sets it as a ratio of retries to requests; AWS uses a token bucket.
- **Retry storm**, **thundering herd** — the failure mode, not the pattern: synchronized retries arriving together.
- **Hedging** — a neighbour, not a retry. Hedging sends a duplicate request to a second replica after a delay, before the first has failed, to cut tail latency. It trades duplicate work for latency rather than for availability.
- **Idempotency key** — the mechanism that makes an operation safe to repeat when the API is not naturally idempotent.

## Context

A call fails. Some failures are transient — a dropped packet, a leader election, a rolling restart, a throttled request — and the same call would succeed a moment later. Others are permanent: the request is malformed, the resource does not exist, a business rule said no.

The caller cannot see which is which. A timeout is the hardest case: the request may have been received, processed, and answered, with only the answer lost. Retrying then repeats the work.

Retry is how a caller converts a partial or random failure into a success. It works only while the failures are a small fraction of traffic. When failures are caused by overload, retries are more load on the thing that is already failing, and AWS's phrasing is exact: retries are selfish. A client that retries is demanding more of the server's time for its own request.

## Forces

- **Transience against permanence** — the same status code can mean either, and eventual consistency blurs the line further.
- **Latency against success** — each attempt buys a chance to succeed and costs the caller time. The caller has a deadline.
- **Load against recovery** — retries arrive exactly when the dependency is weakest, and can keep it down after the original trigger is gone.
- **Duplication against correctness** — a timeout does not mean the work did not happen.
- **Amplification against depth** — retries multiply at every layer that runs them.
- **Visibility** — a retry that succeeds hides the failure that caused it. The final success rate looks healthy.
- **Coordination** — clients cannot coordinate, so each one's reasonable decision sums into an unreasonable whole.

## Solution

Wrap the call in a loop with a policy. The policy answers five questions.

1. **Which outcomes are worth retrying?** Retry only what is transient. A connection reset or a timeout usually means the request did not land; a `503` may clear; a `429` with a `Retry-After` gives you an explicit schedule. A `400`, a `401`, or a business rejection will never clear. AWS notes that eventual consistency blurs this: a `404` can become a `200` as state propagates.
2. **How many attempts, and by when?** Cap the attempts per request, and fit the whole loop inside the caller's deadline. Google caps a request at three attempts and lets the failure bubble up.
3. **How long to wait?** Back off exponentially so a failing dependency gets progressively more room: `min(cap, base × 2ⁿ)` before attempt `n`. The cap stops the wait growing without bound.
4. **How to keep clients apart?** Add jitter, or every client waits the same amount and retries in lockstep. Full jitter is `random(0, min(cap, base × 2ⁿ))`; equal jitter keeps half the wait fixed; decorrelated jitter grows the maximum from the previous sleep.
5. **Is repetition safe?** Retry only idempotent operations. If the operation is not idempotent, give the server an idempotency key so it can recognise the repeat and return the original result instead of doing the work twice.

Two more rules bound the damage:

- **Cap the fleet, not just the request.** A per-request cap of three attempts caps growth at three times the traffic in the worst case. A per-client retry budget on top — Google's example is retries under 10% of requests — brings that back to about 1.1 times. AWS's SDK does the same with a token bucket: every call may retry while tokens remain, then retries drop to a fixed rate until tokens refill.
- **Retry at one layer.** A five-deep stack with three retries at each layer turns one request into 243 at the database. Pick the layer closest to the caller that understands the failure, and let the layers below fail fast.

Which failures to retry, and which to accept as final:

| Signal | Retry? |
| --- | --- |
| Timeout, connection reset, DNS failure | Usually — the request probably never landed |
| `500`, `502`, `503`, `504` | Usually — server-side and possibly transient |
| `429`, or `503` with `Retry-After` | Yes, after the delay the server named |
| `408 Request Timeout` | Yes |
| `400`, `401`, `403`, `404`, `409`, `422` | No — the request is wrong, or the state is final |
| A business rule that rejected the request | No — the answer will not change |
| A dependency that is at capacity | Not immediately — shed load or queue it for later |

### Watching the herd

Every client that fails at the same instant and waits the same amount retries at the same instant. Set the retries and the base delay, then switch jitter on and off. The bars are the retries landing on the dependency, in 250 ms buckets.

<RetrySimulator />

Two things to look for. Without jitter the retries arrive in tall, evenly spaced spikes, each one the whole fleet at once. With full jitter the spikes collapse into a roughly steady rate. Jitter does not remove the first spike — every client failed together, so their first retries still crowd into the first window — it removes every spike after it.

Nygard's version of this is to take the retry out of the request path entirely: queue the failed call and retry it later, when the dependency has room.

## Variants

- **Immediate retry** — retry with no wait. Correct only for rare failures that clear instantly, such as a corrupted packet. Wrong for anything caused by load.
- **Fixed delay** — the same wait every time. Simple, and synchronises every client that started together.
- **Capped exponential backoff** — `min(cap, base × 2ⁿ)`. The default. Without jitter it clusters.
- **Full jitter** — `random(0, min(cap, base × 2ⁿ))`. In AWS's simulation it does the least work and avoids the clusters; the price is a wider spread of completion times.
- **Equal jitter** — half the wait fixed, half random. Keeps a minimum slowdown, but did slightly more work and took longer than full jitter.
- **Decorrelated jitter** — the maximum grows from the previous sleep. More time, less work than full jitter; the two are close.
- **Per-request attempt budget** — cap the attempts for one logical request. Google's is three, then bubble the failure up.
- **Per-client retry ratio** — cap retries as a fraction of a client's traffic, Google's at about 10%, with adaptive throttling that rejects retries as acceptances fall.
- **Token bucket** — AWS's SDK lets calls retry while tokens remain, then retries at a fixed rate until tokens refill. A local cap on a fleet-wide problem.
- **Server-directed backoff** — honour `Retry-After` on `429` and `503` instead of your own schedule.
- **Hedging** — send to a second replica after a delay without waiting for a failure. Not a retry: it targets tail latency, and it duplicates work on every slow request.
- **Retry later, off the request path** — put the failed call on a queue and retry it out of band. Nygard's delayed retry, and the only version that does not spend the caller's deadline.

## Tradeoffs

- **Latency.** Each attempt adds to the tail. A success on the third attempt costs the caller the first two attempts plus `base` plus `2 × base`, and the caller may not have that budget.
- **Load.** Retries multiply traffic during the incident, up to the attempt cap in the worst case. A retry budget caps the multiplier; it does not remove it.
- **Correctness.** Without idempotency, a retry after a lost response duplicates the side effect. The mechanism to prevent it — an idempotency key and a server that dedupes — is work the caller and the server both have to do.
- **Recovery time.** Retries can keep a dependency overloaded after the trigger is gone, so it never drains and never recovers. AWS calls this the risk that retries delay recovery by keeping load high.
- **Observability.** Final success rate hides retries. A service answering after three attempts looks healthy until you measure first-attempt failures and retry rate, which are the signals that matter.
- **Configuration provenance.** Microsoft notes that retry mechanisms are now common in client libraries, each with its own parameters. The policy running in production may be a library default nobody chose.
- **Coupling with the circuit breaker.** Retry wrapped around a breaker multiplies the probes, and Microsoft's rule is that the retry must stop when the breaker reports a fault that is not transient.

- **Retry storms.** Every client waits the same amount and retries together, so the dependency gets the whole fleet in spikes. The symptom: load charts show evenly spaced bursts, and the dependency recovers between them only to be knocked over again.
- **Amplification across layers.** Each layer retries independently, so the attempts multiply. The symptom: the database is the only thing overloaded, and its callers report only modest error rates.
- **Metastable failure.** Retries sustain the overload after the original trigger is gone, so the system stays broken until retry traffic is shed. Huang et al. found that 11 of the 21 metastable incidents they catalogued were sustained by retries. The symptom: the error rate stays flat while load stays high, and removing the retries is what restores service.
- **Duplicate side effects.** A timeout after the work succeeded is retried, and the work happens twice. The symptom: two charges, two emails, two rows. The fix is an idempotency key the server honours.
- **Retrying permanent errors.** A `404` or a validation failure is retried on the same schedule as a timeout. The symptom: wasted attempts and log noise, and an error that can never clear.
- **No timeout, no cap.** An attempt that hangs holds its thread, and the retries pile on top. The symptom: connection and thread pools exhaust while the dependency is merely slow.
- **Retry around an open breaker.** The breaker refuses, the retry treats the refusal as transient, and the probes multiply. Microsoft's rule: the retry logic must stop when the breaker says the fault is not transient.
- **Hiding the failure.** Only the final outcome is measured, so the retry rate is invisible. The symptom: a healthy success-rate dashboard while a dependency is failing a large share of first attempts.
- **Ignoring `Retry-After`.** The server names a delay and the client uses its own schedule instead. The symptom: hammering a service that told you how long to wait.

## When to reach for it

Reach for it when all of these hold:

- the failure is transient — partial, random, or short-lived;
- the operation is idempotent, or you can give it an idempotency key;
- the caller can absorb the added latency inside its deadline;
- the dependency is not already at capacity, or you have a retry budget or a breaker in front of it;
- you can retry at a single layer and let the layers below fail fast.

Do not reach for it for non-idempotent operations without a key; for permanent errors; when the dependency is saturated and the right move is to shed load or queue the work for later; when an outer layer already retries; when the caller's deadline cannot fit another attempt; or when a [circuit breaker](/reliability/circuit-breaker/) is open and telling you the fault is not transient.

Pair it with explicit timeouts on every attempt, and treat the retry rate as a first-class metric — it is the only thing that shows the failures the retries absorbed.
