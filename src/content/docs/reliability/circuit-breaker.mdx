A circuit breaker wraps every call to a dependency in a proxy that stops calling it once failures cross a threshold. It turns a slow failure that consumes the caller's threads into a fast one, and gives the dependency room to recover. The price is refusing requests that might have succeeded.

## Also known as

The name is stable — Nygard named it in *Release It!* and the electrical metaphor carried — but several neighbouring names get used as if they meant the same thing.

- **Circuit breaker** — the pattern, and the name this page uses.
- **Fail fast** — the behaviour of the open state, not the pattern. Returning an error without keeping state is fail-fast behaviour; the breaker is what decides when to do it.
- **Bulkhead** — the other stability pattern it is confused with. A bulkhead caps how many calls a dependency may hold at once; a breaker stops calling it. Hystrix implements both, which is why they arrive together.
- **Retry** — the opposite instinct, and often wrapped around the breaker by mistake. Microsoft is explicit that retry expects success while the breaker assumes failure.
- **Service-mesh circuit breaker** — the same state machine placed in the sidecar or mesh instead of the application, so the policy is shared across instances.
- **Hystrix and resilience4j** — implementations, not synonyms. Each adds its own vocabulary: sleeps, permitted calls, forced states.

## Context

A service calls another service over the network. Remote calls are not in-memory calls: they can fail, and they can hang until a timeout fires. A hanging call holds a thread, a connection, or a queue slot for its whole duration.

Enough callers against one unresponsive dependency exhaust the caller's own pool, and the caller starts failing too. Nygard calls this a cascading failure, and names integration points as where it starts and circuit breakers plus timeouts as the defence. Retry makes it worse when it wraps the failing call: every failure becomes more load on a dependency that is already struggling.

The dependency may recover on its own in seconds or minutes. The caller needs a way to stop contributing to the problem while it does, and then a way to find out whether it has.

## Forces

- **Fail fast against availability** — refusing a call protects the caller's resources but denies a request that might have worked. Every threshold is a choice about which failure to prefer.
- **Evidence against a timer** — the only proof the dependency is back is a real call. A timer is a guess; a probe costs a real failure if the guess is wrong.
- **Sensitivity against flapping** — trip too eagerly and a transient blip becomes an outage. Trip too late and the breaker protects nothing.
- **Blast radius against state** — one breaker per service is coarse; one per endpoint is fine-grained but multiplies the state someone has to tune and watch.
- **Local state against a shared verdict** — a breaker inside the process needs no coordination and cannot itself fail. A shared breaker gives every instance the same answer and becomes a dependency in the critical path.
- **Fallback honesty** — a degraded answer may be worse than an error, depending on what the caller does with it.
- **Visibility** — an open breaker converts loud, slow failures into quiet, fast ones. Without monitoring, the system can look healthy while a feature is gone.

## Solution

Put a proxy between the caller and the dependency. Every call goes through it, and it keeps one state machine per dependency.

1. **Closed** — calls pass through. The proxy records each outcome. When failures cross a threshold, it trips to open.
2. **Open** — calls fail immediately, without touching the dependency. The caller gets an error or a fallback. A timer runs. When it expires, the breaker moves to half-open.
3. **Half-open** — a small, fixed number of trial calls are allowed through; everything else still fails fast. If the trials succeed, the breaker closes and resets its counters. If any trial fails, it reopens and restarts the timer.

The state machine is the pattern. Everything else is configuration and discipline:

- **Count timeouts as failures.** A dependency that hangs instead of returning an error would otherwise never trip the breaker; the caller just runs out of threads. Pair the breaker with a timeout and count the timeout as a failure. Resilience4j goes further and can also trip on a *slow-call rate*, before errors appear.
- **Do not count the caller's mistakes.** A `400`, a `404`, or a validation error says something about the request, not about the dependency's health. Fowler: "Not all errors should trip the circuit, some should reflect normal failures and be dealt with as part of regular logic." Configure the breaker to count only the failures that mean the dependency failed.
- **Require enough traffic to judge.** Two failures out of three calls at 4am is a 67% failure rate and proves nothing. Resilience4j's `minimumNumberOfCalls` exists for this: below the minimum, the failure rate is not computed and the breaker will not trip.
- **Decide what the caller does when the circuit is open.** Hystrix routes every failure path — a thrown error, an open circuit, a full pool, a timeout — through one fallback. The fallback should be local and must not make another network call, or it inherits the failure it was meant to absorb.
- **Keep the breaker in the process.** Nygard's advice is one breaker per process, not a shared object. A shared breaker adds a remote dependency and a single point of failure; the cost of local state is that each instance forms its own opinion.
- **Expose the state.** A trip is abnormal by definition. Log every transition, alert on open, and let operations force or reset it. Fowler: "Any change in breaker state should be logged and breakers should reveal details of their state for deeper monitoring."

## Variants

- **Consecutive-failure threshold** — reset on any success, trip after N failures in a row. Cheap, and slow to trip when failures are intermittent. This is the simple breaker in Fowler's example.
- **Count-based sliding window** — trip when the failure percentage over the last N calls crosses a threshold. Resilience4j's defaults are 50% over the last 100 calls, with at least 100 calls recorded before the rate is computed.
- **Time-based sliding window** — the last N seconds instead of the last N calls. Better when traffic is uneven; resilience4j supports both.
- **Slow-call rate** — trip on the share of calls slower than a threshold, not only on errors. This catches a dependency that is degrading before it starts failing.
- **Health-check probe** — in the open state, poll a health endpoint on a timer instead of letting the next real call be the probe. Microsoft lists this as an alternative to the timer.
- **Accelerated breaking** — trip immediately on an error that says "try again in N minutes", rather than waiting for the threshold.
- **Manual override** — force the breaker open or closed during an incident. Microsoft lists it; resilience4j exposes `FORCED_OPEN`, `DISABLED`, and `METRICS_ONLY` as explicit states.
- **Service-mesh breaker** — the state machine in the sidecar or mesh, shared across instances, with the decision made per host and per route rather than per call site.
- **Breaker over a queue** — for asynchronous work, the signal is a full queue rather than a failing call. Fowler notes the circuit can break when the queue fills.

## Tradeoffs

- **The request gets worse while the caller gets better.** An open breaker refuses calls that might have succeeded. The user sees a fast error instead of a slow one; a false trip turns a transient blip into a visible outage.
- **Latency of failure improves, latency of success does not.** The point is to spend microseconds instead of a timeout on a doomed call. The work is still not done.
- **The operational surface grows.** Thresholds, windows, cooldowns, fallbacks, and one state machine per dependency. Microsoft warns that a breaker adds overhead, is redundant when retry is enough, and should not substitute for handling business exceptions.
- **Tuning is a guess about recovery.** Too short a cooldown reopens on an unfinished recovery; too long denies traffic after the fault is fixed. Microsoft says to match the breaker to the dependency's likely recovery pattern.
- **State distribution has no free option.** Per-process state, as Nygard recommends, avoids a shared dependency but produces N independent verdicts. Shared state gives one verdict and adds a round trip and a single point of failure.
- **The fallback decides whether any of this helped.** Stale or empty data can be worse than an error, and a fallback that calls the network inherits the outage.
- **Testability.** The open and half-open paths are the ones normal traffic never exercises. They need fault injection, or they ship untested.

- **Trips on the caller's errors.** Counting `4xx` or business exceptions as dependency failures. The symptom: the breaker opens during a burst of bad requests while the dependency is healthy, and closes when the bad requests stop.
- **Never trips on a hang.** Counting only exceptions while the dependency is slow rather than erroring. The symptom: the breaker stays closed while latency and thread counts climb, until the caller falls over.
- **Flaps at low traffic.** A percentage threshold with no minimum call count. The symptom: the breaker opens on two or three failures at 4am and closes on the next success.
- **Half-open is per instance.** A probe budget of one is one per process, not one per fleet. The symptom: the dependency sees a burst at every cooldown expiry. Spread the probes, or move the breaker to the mesh.
- **The recovery avalanche.** The traffic held back while open returns all at once, against a dependency that scaled down during the quiet period. The probes succeeded on a cold, idle service; full traffic knocks it over. Zalando's case: the breaker stayed open for hours, probes passed at 15 ms, and the released traffic overwhelmed three pods — then the cycle repeated. The symptom: the breaker closes, the dependency times out, the breaker reopens, on a loop.
- **Retry around the breaker.** Retry treats the breaker's fast failure as transient and multiplies attempts; in half-open it multiplies probes. Microsoft: retry logic must stop when the breaker says the fault is not transient. The symptom: load on the dependency during recovery is higher than during normal operation.
- **No fallback.** The breaker opens and every caller gets an error. The caller's threads are saved, the user's request is not. The symptom: a total failure for a dependency that is receiving no traffic.
- **An invisible trip.** Nothing alerts on open, or the fallback swallows the fast failure. The symptom: dashboards look normal while a feature is silently degraded.
- **One breaker for everything.** A single breaker for a whole service, so one bad endpoint opens the circuit for every operation. The symptom: unrelated features fail together.
- **Per-instance blind spots.** One instance trips, another does not, and the second keeps sending traffic to the sick dependency. The symptom: a partial, inconsistent outage that looks like flakiness.

## When to reach for it

Reach for it when all of these hold:

- the dependency is remote and can fail independently of the caller;
- a failed or hanging call costs the caller a thread, a connection, or a queue slot, so waiting is expensive;
- a fast error is better than a slow one, and the caller has something to do with it — a fallback, a degraded response, or an error the user can act on;
- the fault is likely to last long enough for a cooldown to matter, rather than being a single dropped packet;
- someone will watch the breaker's state.

Do not reach for it when the call is in-process, where Microsoft notes it only adds overhead; when a retry is sufficient and the dependency is built for retries; when every request must succeed and no degraded answer is acceptable — a [work queue](/messaging/work-queue/) or backpressure is the better tool; or when the platform already provides it at the mesh or load balancer. It is not a substitute for handling business errors, and it does not fix the capacity of the dependency.

Like the other stability patterns, it is a decision about one integration point, not an architecture style. It says how a call fails, not how the application is organised.
