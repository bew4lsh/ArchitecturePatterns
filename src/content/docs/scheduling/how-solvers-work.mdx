A solver is not a function that returns the best schedule. It is a search that runs under a time budget and returns the best schedule it has found. Understanding what happens inside explains why the model is the artefact you version, why the answer can vary between runs, and why a solver belongs behind a queue rather than in a request handler.

## The model is the interface

Everything starts with a declarative model: variables with domains, constraints over them, and an objective. For scheduling, OR-Tools' CP-SAT offers variables that mean "this task starts at time *t*" and constraints that mean "these tasks may not overlap" or "these tasks share a machine of capacity *n*". Nothing in the model says how to search.

That separation is the first architectural fact. The constraints are business rules; the search is the solver's business. A rule change should be a model change, not an engine change.

OR-Tools is a suite, and the engine follows the model: CP-SAT for integer programs with rich logical constraints, MPSolver for linear and mixed-integer programs, and the routing library — local search over a CP core — for vehicle routing. CP-SAT works over the integers, so fractional data has to be scaled into whole numbers first.

## Presolve and propagation

Before any search, the solver narrows the problem. **Presolve** removes variables and constraints that cannot matter, fixes values that are forced, and detects some infeasibilities outright. **Propagation** then uses each constraint to shrink the domains of the variables it touches: if task B must follow task A and A cannot finish before 10, then B cannot start before 10. Repeat that across constraints and some problems are solved, or proven impossible, without a single guess.

This is why a solver can answer "infeasible" quickly and correctly. It can also spend a long time proving infeasibility: the answer is a proof, not a guess.

## Three engines, and the one CP-SAT uses

A combinatorial solver is usually built from one of three engines, or from a mix:

| Engine | Idea | Strong at |
| --- | --- | --- |
| Constraint programming | propagate constraints to shrink domains, then branch and backtrack | sequencing, feasibility, logical constraints |
| Mixed integer programming | relax to a linear program, branch on fractional variables, add cuts | linear objectives, proving bounds |
| Local search | move from solution to solution inside a neighbourhood | routing, very large instances, anytime output |

CP-SAT is constraint programming rebuilt on top of a SAT engine, with a simplex alongside and local search folded in. The scheduling constraints — no-overlap, cumulative capacity — are a rich modelling layer; the search underneath is not the classic CP search. That combination is what produced the recent closed-problem results on job-shop and resource-constrained project scheduling benchmarks, where the scheduling constraints and the SAT core reinforce each other.

## Lazy clause generation

The idea that makes it work is **lazy clause generation**. A propagator that removes a value from a domain also produces an explanation for why: the reason, as a logical clause. Feed those explanations to a Conflict-Driven Clause Learning (CDCL) SAT solver and it does what SAT solvers do — when a branch leads to conflict, it derives a *nogood*, a clause that rules out the whole family of assignments with the same cause, and jumps back to the decision that mattered rather than the most recent one.

The effect is that the search stops repeating its mistakes, and it stops them exponentially: one learned clause can remove an enormous subtree. It also changes the economics of the solver. Expensive propagation is worth running when its explanations are reused, and that is why a simplex sits inside a constraint solver at all.

## A portfolio, not a search

CP-SAT does not run one search. It runs a set of workers with different personalities: complete searches with different branching heuristics, workers that focus on feasible solutions, workers that run large neighbourhood search, and background probing that strengthens bounds. They rarely share a tree; they share results.

A set of thread-safe managers sits between them. The response manager holds the best solution and the objective bound. The bounds manager propagates tightened variable domains found by one worker to the others. The solution repository keeps a pool of diverse feasible solutions to seed later searches. The time limit is shared, so the whole run stops together.

For a scheduling model, a large part of that effort is **large neighbourhood search**: keep most of the schedule fixed, free a subset of tasks, and re-solve the much smaller subproblem. The submodel is presolved on its own and solved with a short limit, and a better solution goes back into the pool. Specialised generators pick the neighbourhood by time window, by resource, or by the difference between the current solution and the linear relaxation (RINS).

## What the solver promises

The return value is a status, not just an answer: **OPTIMAL** (proven best), **FEASIBLE** (a solution, optimality unknown), **INFEASIBLE** (proven impossible), **UNKNOWN** (stopped before either), or **MODEL_INVALID**. A time limit turns a hard model into a FEASIBLE answer with a proven bound on how far it can be from optimal. A callback receives each improving solution as it is found, which is what makes the workflow anytime.

Two consequences follow. First, "we asked for the optimum" and "we proved the optimum" are different claims, and a schedule shipped from a timed-out solve carries a gap. Second, parallelism costs reproducibility: with several workers the search interleaves and the run is not repeatable. Fixing the worker count to one and setting the random seed is how you get the same answer twice.

### Watching propagation and the budget

Full bounds propagation proves the optimal schedule in a few thousand nodes. Switch propagation off and the same proof needs more than a million, or never arrives before the budget runs out. The step chart is the anytime answer: the best makespan found so far, falling toward the lower bound, and the gap that a budget leaves behind.

## What this means for the system around it

- **Version the model, not the schedule.** The model is the thing a rule change edits; the schedule is an output.
- **Treat the solver as a CPU-bound worker.** It runs for seconds to hours, holds no useful state between runs, and belongs behind a queue with a time budget — not in a request handler.
- **Make the time budget the contract.** Ask for "best within 30 seconds", and record the bound on what came back.
- **Check feasibility independently.** A solver bug or a modelling mistake produces a confident schedule; a separate feasibility checker catches it before it ships.
- **Keep determinism where you need it.** One worker and a fixed seed for reproducible tests; many workers and a time budget for production.
- **Watch the model, not the search.** Presolve and clause learning make the same problem cheap or expensive depending on how it is written, and that is the lever you control.
