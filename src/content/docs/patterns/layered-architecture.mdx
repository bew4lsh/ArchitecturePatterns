## Context

You are building a business application — a system whose complexity lives in rules rather than in algorithms. It has a user interface, some domain logic, and some persistence, and the team is small enough that everyone works in the same codebase. Nothing yet forces the pieces apart.

The style carries three names for the same arrangement. Richards and Ford call it the **layered architecture**, also **n-tiered**; Buschmann and others, in *Pattern-Oriented Software Architecture*, call the general form **Layers**; Microsoft's catalogue calls the style **N-tier**. The names agree, and this page uses the first.

Two parts of that vocabulary are worth separating. **Layers are logical, tiers are physical:** a layer is a group of code with a dependency rule, a tier is a machine boundary, and "n-tiered" names the logical style from an era when each layer had its own box. A layered monolith and a four-machine deployment are the same style with the tiers switched on. And this is the style a system arrives at **by default** — Richards and Ford observe that a team which starts coding without choosing a style usually lands here, which they name *architecture by implication*.

## Forces

- **Separation of concerns** — UI code and business rules change for different reasons and at different rates.
- **Testability** — domain rules should be exercisable without a database or an HTTP request.
- **Onboarding** — a new contributor needs an obvious place to put things.
- **Change cost** — a naive layering adds indirection to every call, so the boundary has to earn its place.

## Solution

Organise the code into horizontal layers, each with a single responsibility, and allow a layer to talk only to the one directly beneath it.

The rules that make this more than a folder convention:

1. **A layer may only call the layer directly below it.** Presentation does not reach into Persistence; it goes through Application.
2. **A request descends, a response ascends.** Data crossing a boundary is translated at it — a domain object does not become an HTTP response in the domain layer.
3. **A layer owns its abstractions.** The Domain layer defines the interface it needs; Persistence implements it. That inverts the compile-time dependency even though the runtime call still goes downward.

Rule 3 is the one people miss, and it is the difference between a layering that is testable and one that merely looks tidy.

## Variants

- **Relaxed layers** — a layer may skip downward past its neighbour (Presentation may call Domain directly for simple reads). Cheap, and it tends to become the rule rather than the exception.
- **Open layers** — a boundary that requests may pass straight through. Usually justified exactly once, for a shared utility layer.
- **Strict layers** — every boundary closed. What this page describes, and the version that ages best.
- **Ports and adapters** — the Domain at the centre with all I/O at the edges. This is a layered architecture with Rule 3 taken seriously and the diagram rotated 90°, not a different idea.

## Tradeoffs

- **Modifiability** is good for changes that stay inside one layer, and poor for changes that are genuinely cross-cutting (a new field on a form that must be persisted usually touches four layers).
- **Testability** of the Domain layer is high; the layers above it are usually testable only through their boundary.
- **Deployability** is unchanged: one unit, released together. Layering buys nothing here.
- **Performance** gains a call hop per layer and a translation at each boundary. Usually noise; visible in tight loops and in mapping-heavy read paths.
- **Onboarding** improves, genuinely. This is the pattern's most reliable payoff.

## Failure modes

- **The sinkhole** — every request is a pass-through with no logic in the middle layers. The layers are pure ceremony, and you are paying indirection for nothing.
- **Layer leakage** — a domain entity with `@JsonProperty` annotations, or a repository returning `ResultSet`. Once a lower layer knows about an upper layer's format, the boundary is decorative.
- **Fat persistence** — business rules migrating into stored procedures or ORM hooks, because that is where the data is.
- **Skipped layers by convention drift** — "just this once" from Presentation to Persistence, and then the diagram becomes a lie.

## When to reach for it

Reach for it when the domain is rule-heavy, the team is more than one person, and the system ships as a single unit. It is the right default precisely because it is cheap and because it fails loudly: a sinkhole is visible in a diff, whereas a distributed mess is not.

Do not reach for it when the application is mostly CRUD over a database — that is where the sinkhole comes from — or when you are already paying for a distributed system, where the layering should follow the services instead.
