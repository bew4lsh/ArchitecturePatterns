A work queue is the pattern behind every background job system: a producer writes a task to a queue, and a pool of interchangeable workers each take one task at a time. It is also the pattern people reach for without noticing they have, usually after giving a web request more work than a web request should do.

## Context

Work arrives as units that are independent of one another — resize this image, send that email, recompute this report. The caller does not need the result to continue, and the work is heavier than the request that triggers it.

Two rates are now in play, and they are not the same rate. Requests arrive in bursts; work is consumed at whatever rate workers can manage.

This pattern is named in several places under different names, because each describes a different part of it. RabbitMQ's tutorial calls it a **work queue**, also **task queue**. Enterprise Integration Patterns describes the consumer side as **competing consumers**. Microsoft's catalog splits it into **Queue-Based Load Leveling** for the burst-buffering framing and names the resulting architecture style **web-queue-worker**. There is no single settled name, so this page uses the mechanism's.

## Forces

- **Rate mismatch** — arrival rate is variable, processing rate is roughly fixed.
- **Latency tolerance** — the caller can accept a delayed answer, or no direct answer at all.
- **Cost** — provisioning for peak load is wasteful if bursts are rare and brief.
- **Failure** — a worker can die mid-task, and the task still needs doing.
- **Ordering** — sometimes it matters, and it is the first thing a queue gives up.
- **Visibility** — once work is deferred, nobody is watching it unless you make them.

## Solution

Put a queue between the producer and the workers, and make the workers interchangeable.

1. The producer writes **one message per unit of work** and returns. The message must carry everything the worker needs; a worker reaching back into the producer's state defeats the point.
2. The queue stores messages until a worker takes one. A message goes to **exactly one** worker — this is point-to-point, not publish-subscribe.
3. Workers pull, process, and **acknowledge**. Acknowledgement means "done, delete it", not "received".
4. If a worker dies without acknowledging, the queue **redelivers** the message to another worker.

Step 4 is the part that makes the pattern worth its complexity, and step 4 is also why your handlers must be idempotent: a worker that finished the work and crashed before acknowledging will cause that work to be done a second time.

## Variants

- **Competing consumers** — the Enterprise Integration Patterns name for several consumers on one point-to-point channel. Requires a point-to-point channel specifically; on a publish-subscribe channel, extra consumers get extra *copies*, not extra throughput.
- **Queue-based load leveling** — the same structure with the emphasis on protecting a downstream dependency from bursts, so it can be provisioned for average load.
- **Web-queue-worker** — the architecture style that results when this becomes the spine of the system: stateless web tier, queue, stateless worker tier.
- **Priority queue** — several queues with different service rates, or a queue that reorders. Usually a sign that one queue is being asked to serve two different latency expectations.
- **Delayed or scheduled queues** — the message becomes visible at a future time. Turns the pattern into a scheduler.
- **FIFO with message groups** — ordering is preserved within a group key rather than globally, which is the only kind of ordering most systems actually need.
- **Partitioned logs (Kafka)** — each partition is the real point-to-point channel and a router assigns messages by key. Consumers in a group do not truly compete: an idle consumer cannot help a partition that is backed up, and the group can never exceed the partition count.

## Tradeoffs

- **Deployability and independence** improve in the way that matters: workers are stateless and crash-tolerant, so they can be restarted, rescaled, and replaced at will.
- **Cost** improves for bursty work — you provision for average throughput, not peak. Idle workers and queue storage are the price, usually a good trade.
- **Availability** improves for the producer: it can keep accepting work while workers are down, because the queue holds the backlog. The broker becomes a hard dependency in exchange, and it is now in the critical path of everything.
- **Latency** gets worse, and not just by one hop. Queuing delay is the dominant term: with a backlog, p99 latency is a function of queue depth divided by throughput, not of how fast the handler is.
- **Ordering** is lost as soon as more than one worker runs. Getting it back costs throughput.
- **Operability** grows a new signal that must be watched: queue depth. It is the only thing that tells you the system is falling behind.
- **Backpressure** does not exist unless you build it. A queue accepts everything offered to it, which is why "the queue is our buffer" so often becomes "the queue is where work goes to die".

- **Queuing work that needed an answer** — once enqueueing is cheap, everything gets queued, including work the caller is waiting on. The system acquires a latency profile nobody chose, and one that is invisible in the code that enqueues.
- **Rate mismatch** — if the average producer rate exceeds the average consumer rate, the queue grows forever. Queuing does not fix this; it only converts a visible failure into an invisible one.
- **Poison messages** — a message that always fails cycles indefinitely. Route it to a dead-letter queue after a bounded number of attempts, and alert on that queue's depth, because an unmonitored dead-letter queue is a silent data-loss channel.
- **Forgotten acknowledgement** — the worker does the work but never acks. The broker holds every unacknowledged message in memory and redelivers them all when the worker disconnects, which looks like random duplication. In RabbitMQ this also grows broker memory without bound.
- **Duplicate processing** — at-least-once delivery is the norm, so a crash between committing the work and sending the ack causes the work to be repeated. Without an idempotent receiver, that is a duplicate charge or a duplicate record.
- **Unbounded downstream rate** — autoscaling consumers against queue depth without capping their aggregate rate onto the next dependency moves the overload one hop downstream, where it is harder to see.
- **Wasted work** — a backlog makes it easy to process work that no longer matters. Give messages a deadline or a TTL, and let the worker discard expired ones rather than doing them carefully.
- **Uneven workers** — round-robin dispatch is blind to task weight, so a queue of mixed-difficulty tasks leaves one worker saturated while others idle. Limiting each worker to one unacknowledged message at a time (`prefetch = 1`) fixes it by dispatching to whoever is free.

## When to reach for it

Reach for it when the work is independent, the caller can wait, and demand is bursty. The pattern's real payoff is provisioning for average load while surviving peak load, and it gets a second payoff almost for free: workers become restartable, because the queue remembers the work.

Do not reach for it when the caller needs a synchronous low-latency answer — that is a different pattern, and adding a queue in front of a synchronous call mostly adds a timeout you now have to tune. Do not reach for it when volume is low and stable, where the queue is complexity that never pays for itself. Do not reach for it to get ordering: it takes ordering away by design.

Also worth being clear about scope: this is not an alternative to a structural style like [Layered Architecture](/patterns/layered-architecture/). It says how work is distributed, not how an application is organised, and most systems that use it are also layered internally.
